🧭 What routeperf Actually Does

Most API tools only tell you whether an endpoint is up. They do not tell you whether it is fast, and they certainly do not tell you what happens to that endpoint once your database has ten million rows instead of ten thousand.

routeperf fills that gap. It reads the OpenAPI (also called Swagger) file that describes your API — the same file your team probably already has — and matches each endpoint to the database queries it uses. It then asks PostgreSQL or MySQL to explain how it would run those queries using the built-in EXPLAIN ANALYZE feature.

The result is a short, readable report for every endpoint: how long it really takes, which query inside it is the bottleneck, and how its cost grows as your tables grow. That growth pattern is the "Big O" part of the name, and it is the single best early warning sign that a feature will fail under real traffic.

You do not need to read source code, install a database plugin, or change anything in your application. routeperf runs on your own computer, connects to a database you choose, and prints its findings to your screen. Nothing is uploaded anywhere.

✨ What You Get

  • A per-endpoint scorecard. Every route in your API file gets a line in the report, with its measured timing and a simple rating.
  • Big O growth estimates. See whether an endpoint stays flat as data grows, grows in a straight line, or explodes as a square of the data size.
  • N+1 query detection. The classic hidden slowdown — one request quietly firing hundreds of small database trips — gets flagged clearly.
  • Real query plans. Sequential scans, missing indexes, and expensive joins are pulled straight from your database's own planner.
  • PostgreSQL and MySQL support. Use whichever database you already have running.
  • OpenAPI and Swagger input. Point it at the spec file you already maintain.
  • A single command-line run. No background service, no agent, no accounts, no sign-up.
  • Shareable output. Copy the report into a ticket, a chat message, or a pull request so everyone sees the same numbers.

💻 What You Need Before Starting

  • A Windows 10 or Windows 11 computer.
  • An OpenAPI or Swagger file for the API you want to measure, saved somewhere you can find it again.
  • A PostgreSQL or MySQL database you are allowed to connect to. A copy on your own machine is perfectly fine.
  • The login details for that database: host, port, database name, username, and password.

That is the whole list. You do not need a programming environment, a compiler, or any knowledge of the Go language that routeperf is written in.

Step 1 — Get the application.

The page you land on is the public home of the project. Follow the download link shown there to save routeperf to your computer.

Step 2 — Keep it in one folder.

Create a new folder somewhere easy to remember, for example C:\routeperf. Put the downloaded file inside it. Keeping everything in one place means you will never lose track of the tool, your API file, or your notes.

Step 3 — Open a terminal in that folder.

Open File Explorer, go into your new folder, click once on the address bar at the top, type cmd, and press Enter. A black window opens, already pointed at your folder. This is where you will type your commands.

Step 4 — Check that it is there.

In that black window, type the name of the program and press Enter. If you see usage information — a short list of options — you are ready. If Windows says it cannot find the file, the file is not in that folder; move it there and try again.

▶️ Your First Run

A run needs three pieces of information: where your API file is, which database to talk to, and which kind of database it is. In the same black window, type a line like this and press Enter:

routeperf --spec C:\routeperf\api.json --db postgres --host localhost --port 5432 --name mydb --user postgres

For a MySQL database, the line looks almost the same, with the database type and port changed:

routeperf --spec C:\routeperf\api.json --db mysql --host localhost --port 3306 --name mydb --user root

If your database asks for a password, it will prompt you before anything runs. Type it and press Enter; nothing is stored anywhere.

Reading what comes back

routeperf prints one block per endpoint. Each block shows the endpoint's path and method, its measured duration, a Big O growth label, and a short note about what the database planner found. Look for three things first:

  • Endpoints that grow quickly. A label showing growth that scales with the square of your data is the biggest red flag in the whole report.
  • Endpoints flagged as N+1. These are usually fine on a test database and terrible in production. Fix them before launch, not after.
  • Large sequential scans. When the plan says the database is reading an entire table for a single lookup, a missing index is the likely cause.

Run routeperf again after you add an index or change a query. Watching the numbers move is the fastest way to know whether a fix actually helped.

🩺 If Something Goes Wrong

The black window says the program is not recognised

The file is not in the folder your window is pointed at. Close the window, go back into the folder, and repeat the step that opens the command prompt from inside it.

It cannot connect to the database

Check the host, port, database name, and username one at a time. The port is the most common mistake: PostgreSQL normally uses 5432, MySQL normally uses 3306. Also confirm your database is actually running — open your database tool and check it responds there first.

It says your API file cannot be read

Check the path after --spec. It must point at the file itself, not just the folder it lives in, and the file should end in .json or .yaml. A quick way to test the path is to paste it into File Explorer's address bar; if the file opens, the path is correct.

The report is empty

An empty report usually means the API file was found but contained no routes routeperf could match. Confirm the file describes at least one endpoint with a path and a method.

The numbers look too fast to be true

If your database is empty or very small, everything will look fast and flat. Load a realistic amount of sample data first, then run the report again. Performance problems only show themselves once there is enough data for the database to make real decisions.

  • Testers and QA engineers who want to report a slow endpoint with evidence instead of a vague complaint.
  • Backend developers who want to catch an N+1 query before it reaches production.
  • Database administrators who want a quick per-endpoint view of index usage without a full profiling suite.
  • Team leads and product owners who need to decide what to fix first based on real numbers rather than guesswork.
  • Students and learners who want to see what Big O growth looks like in a real database instead of a textbook.

📖 A Few Words, Explained Simply

  • OpenAPI / Swagger file. A text file that lists every address your API answers and what it expects. Think of it as a menu for your API.
  • EXPLAIN ANALYZE. A feature built into PostgreSQL and MySQL that reports exactly how the database intends to fetch your data, and how long it took.
  • Big O. Shorthand for "how does the work grow as the data grows." Flat is great, a straight line is acceptable, a sharp curve is a warning.
  • N+1 query. When one request accidentally triggers hundreds of separate database trips — one for a list, then one for each item in it.
  • Full table scan. The database reads every row in a table to answer a question. Fine for a hundred rows, painful for a million.
